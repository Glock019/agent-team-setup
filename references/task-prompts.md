# 团队配置后的任务提示词

## 配置交付

每次首次配置团队或修改成员后，默认直接给出成员表和简短保存结果，内部准备每位成员的派活上下文。用户要求查看提示词时，附上每人一条填好代号、职责、模型和强度的提示词，仅把真正未知的任务、材料和交付目标留为占位符。使用固定代号 `M1`、`M2`、`M3`，与预设 A–H 区分，展示为“成员1、成员2、成员3”；代号在同一项目中不因完成、暂停或展示顺序改变而重新编号。成员增加时使用新代号。

同时在成员表前说明派活方式（自动拆分或手动派活）和启动方式（等待开始或直接执行）。

配置收到后由主 Agent 自动保存并准备分工及内部派活上下文。下方可复制提示词仅供用户以后指定任务或覆盖自动分工，不要求用户逐条发送才能让配置生效。自动拆分时，已提供目标和材料即可由主 Agent 安排成员；保存配置不替代用户选择的“开始”指令。

成员表字段：成员代号、角色、配置模型、推理强度、当前任务、写入范围、状态。尚未派活写“待分配 / 已配置未启动”；已启动后维护代号与实际工具返回的 agent ID 映射，不向用户假称一个配置槽位已经是运行中的进程。配置与任务通过项目持久记录延续；跨对话读取项目记录并展示交接摘要，等待用户说“开始”，不承诺保留原进程。

每个成员可接收多个先后执行的任务。模型与强度不变且线程仍可用时复用现有成员；仅配置尚未启动则首次创建。改变模型或强度时，按工具能力启动新实例并交接任务，不声称原实例已经热切换。旧实例仍在运行时先停止冲突写入，确认状态再交接。

## 启动方式

默认用户派活后先整理任务和分工，等待“开始”，此时不创建执行任务的子 Agent。收到“开始”后针对已展示计划执行，不要求逐个成员重复确认。新任务或实质变更重新展示受影响部分并按所选启动方式处理；已授权任务的正常跟进不反复暂停。用户明确选择直接执行时，将下面模板中的等待句替换为“展示分工后直接执行”。

## 用户可复制的提示词

以下方括号是待填字段。用户要求查看提示词时，为每名成员输出“单人派活”的具体版本，并给出一条批量派活示例。其余模板按需展示，避免每轮重复全部模板。

### 单人派活

给 [成员代号与角色] 分配任务：沿用已配置的 [完整模型 ID]、[推理强度]。目标是 [具体问题或修改目标]，输入材料为 [文件、路径或本轮附件]；允许修改 [明确范围，或只读]；交付 [结果形式和验收要求]。请由主 Agent 补齐上下文并展示分工，等我说“开始”后分派，完成后核实并汇总。

### 批量派活

沿用当前团队：M1 负责 [任务一]，M2 负责 [任务二]，M3 负责 [任务三，如有]。共用输入为 [材料]，各自可改范围为 [范围，或全部只读]。先检查依赖和写入冲突，展示分工，等我说“开始”后执行，其中独立部分并行，最后由主 Agent 集成并按 [标准] 验收。

### 由主 Agent 自动拆分

沿用当前团队，目标是 [整体任务]。请根据成员能力自动拆分任务，列出成员职责、输入、可改范围和验收标准，等我说“开始”后执行；依赖步骤按顺序推进，无需我逐个派活。

### 补充任务或调整优先级

给 M2 补充 [新信息]；当前目标调整为 [目标]，优先完成 [事项]。请检查它当前状态，必要时中断旧工作再交接，其他成员继续原任务；如涉及接口或共享文件变化，请通知受影响成员。

### 查询进度

汇报当前团队进度：每个成员实际已完成什么、正在做什么、哪些任务被阻塞，以及下一步是什么。只报告已获得的状态和证据，不猜测完成百分比。

### 暂停与继续

暂停 M1，保留已完成的变更和任务摘要，不再开始新任务；确认实际停止状态。需要继续时，沿用 M1 的配置，从最后完成事项接着处理 [剩余目标]；原线程不可用则重建并明确说明。

### 跨对话交接

为当前团队生成可复制的交接摘要：成员代号、模型和强度、文件范围、已完成和待办、依赖、验证结果及输入文件位置。保存到项目记录。新对话重新核对材料版本、模型可用性、升级历史和写入负责会话，展示交接摘要，等我说“开始”再创建需要的成员，不假设旧线程仍存在。

## 主 Agent 发给子 Agent 的执行提示词

使用下面结构填入本次任务的实际信息后再调用工具；模型和强度必须写入真实调用参数，不能只写在自然语言提示词里。只传必要上下文，不能要求子 Agent 自行访问它看不到的主对话或附件。先解析实际输入路径，不把占位符传给执行者。

```text
成员与任务：[项目标识 / M编号 / 角色 / 根任务T编号 / 修订号]
目标：[一个明确的目标及其与总任务的关系]
输入：[可访问的实际文件路径及版本或快照、用户要求、原始证据]
上下文与接口：[已确认约定、必要决策、前置任务结果]
写入范围：[确切文件或目录，或只读；独立 worktree 的实际目录]
约束：[不可修改的公共文件、运行资源分配和任务特定限制]
验收：[可核实的完成条件；适用的测试或证据]
交付：[结论或改动、对应版本、证据位置、逐项验收状态、剩余问题；报告完成后待主Agent验收]
协作：[跨范围需求向主 Agent 回报，不覆盖其他成员工作，不再委派]
```

未写明范围的审核任务默认为只读；明确的修改请求可由主 Agent 从任务推导最小范围并公开说明，不把模板未填满变成反复确认的理由。文件不可访问、目标存在关键歧义时只问必要问题；继续推进不依赖缺失信息的部分。

成员报告完成时将任务置为“待验收”，主 Agent 按版本核实后才置为“完成”，不要把成员代号删除。收到新任务时依据真实线程状态决定发送跟进还是创建新实例。每次分派后说明实际启动/排队/阻塞结果，不把计划当作执行结果。

G/H 的测试岗位先从原始需求制定用例和复现条件，与实现并行；验证新代码时在任务台账中明确依赖实现产物，并返回对应版本、命令、实际结果和未验证项。最终审查同时读取代码与同版本测试证据。没有可独立执行的测试工作时，不启动空岗位，由主 Agent 完成验证并明确证据来源；不虚构成员已完成。

### 恢复项目

使用 $agent-team-setup 恢复 [项目名称或记录位置]。读取团队、任务、证据与升级记录，核对文件版本和旧会话状态，展示交接摘要，等我说“开始”再继续。

### 查看验收记录

展示 [任务编号或成员代号] 的任务记录、原始证据位置和验收清单，区分成员自报完成、主 Agent 已核实及尚未验证的事项。
