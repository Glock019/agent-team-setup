# 长期项目、升级与验收

## 项目身份与持久记录

将成员视为项目内稳定岗位，而不是永久在线进程。维护稳定的项目标识、M成员代号、T任务编号及任务修订号；跨对话保留这些身份，实际执行实例可重建。不得因重建、拆分子任务或换对话重置重试和升级计数。成员转交任务时保留前任记录。

首次确定项目时建立唯一的项目记录位置。已有外部 Git 项目在项目内维护 `agent-team/`（或用户指定位置），按该项目规则保存，不重复保存整个仓库到其他位置。非仓库项目使用当前环境的持久文件能力；在 ChatGPT Work 通过可用 Library skill 保存和更新同一组项目文件。不要将用户项目状态写入本 Skill 目录或全局配置。只有临时空间可用时，说明无法保证跨对话保留并提供可带走的交接内容，不声称已持久保存。

按实际需要维护以下文件，首次可只建立配置与台账，其余随事件创建：

| 文件 | 内容 |
|---|---|
| `team.json` | schema_version、项目标识、配置版本、M成员/模型/强度/职责/范围、派活与启动方式、并发及重试边界、当前写入负责会话 |
| `tasks.json` | T编号、根任务编号、修订号、负责人、依赖、输入版本、范围、验收条件、状态、产物位置、重试计数 |
| `events.jsonl` | 追加式关键操作、UTC时间、成员、任务、配置变更、失败与重试、用户决策、升级授权及实际结果 |
| `tasks/Txxx.md` | 该任务每位参与者的执行摘要、证据索引、交接内容和验收清单 |
| `handoff.md` | 最新整体进展、配置摘要、阻碍、下一步、文件版本与可访问位置、未完成授权及升级历史摘要 |

记录可核实的操作和判断依据，不收集或要求内部思维过程。证据尽量引用原始产物与必要日志，不重复存放整份大文件。保存记录时保留来源版本；仅主 Agent 更新团队公共台账，成员返回证据或写入自己的任务产物，避免并发覆盖。

在任务完成、关键决策、实际升级、阻碍、范围变更和主动交接时保存检查点，不等到对话结束。保存成功后才声称检查点可恢复。失败时明确告知未保存内容和最近成功版本，保留可恢复副本，不继续声称项目记录最新。

## 新对话恢复与多会话协调

1. 定位同一项目的持久记录；若项目身份有歧义，只问必要问题，不把两个项目合并。
2. 读取团队、任务台账、近期升级事件和交接摘要；检查文件访问、实际版本、模型能力与旧实例状态。旧时间戳或缺少心跳不证明旧进程停止。
3. 展示恢复摘要：团队配置、已完成、待验收、待执行、阻碍、变更及计划。将旧会话的“运行中”视为待核实，不能直接恢复成活跃。
4. **每次跨对话恢复，默认等待用户说“开始”后才启动、继续或重建执行成员**，即使旧会话已批准执行。恢复前可只读核对和准备摘要。用户在本次恢复请求中明确要求直接继续可覆盖此偏好，历史会话的直接执行设置不能自动覆盖。

默认一个会话负责项目写入和集成，其他会话只读。记录负责会话及状态；记录是协调信息，不是互斥锁。有原子锁/租约能力时使用并检查所有者；没有时不得声称已锁定。无法核实旧写入者状态则暂停冲突写入，先协调停止或隔离到独立工作区；不强删别人的锁、不强制覆盖旧变更。接管后检查未提交差异、未完成工具操作及产物版本，再继续。

## 推理强度升级

用户授权主 Agent 在同一模型内提高子 Agent 的推理强度，必须在实施前明确告知成员、任务、原因、旧等级、新等级和预期验证点。提高强度应基于具体未解决风险或失败证据，不因任务长就机械升级。主 Agent 自身不能通过文字声称切换自己的运行配置。

按当前工具支持的强度顺序检查，默认提高到足以解决问题的下一档，不用一次跳最高档规避次数规则。首次配置、用户直接指定的强度不是自主升级事件；新实例执行同一强度也不重复计数。

在拟实施升级前检查两个阈值，任一触发则先申请用户同意：

- 同一根任务将发生**第二次或更多**自主提高；换成员或拆成子任务不清零。
- 全团队过去滚动 **30 分钟**内已有两次实际提高，本次将是**第三次或更多**。

计数包含已批准并实际执行的提高。按根任务累计与 UTC 时间记录，跨会话延续；记录不完整无法判断是否超限时，不假定为零，说明缺失并先询问。失败的配置申请不算成功提高，但需记录失败。初始任务强度已高于预设由用户主动指定时不算自动升级。

申请时给出阈值、最近升级记录、失败证据和拟采用设置，用直接自然语言询问，不能把权限审批塞进偏好选择工具。用户同意仅覆盖说明的范围，不重置计数；若用户明确批准一定次数或时间范围，记录覆盖边界。最高强度仍受阻时交付诊断和选项，不无限重试。**更换模型单独征求同意**，除非已得到清晰、适用的模型适配授权；提高推理强度的许可不包含换模型。

工具不支持在线变更时保存检查点、确认旧成员停止冲突写入，再以相同M代号创建新实例。保留旧实例与新实例映射，不称为热切换。只记录实际工具执行的配置，不把请求值当作已生效。

## 运行边界与失败处理

配置时公开最大并发，默认为选定预设需要的数量且不超过环境上限。不要无任务扩编或让成员递归委派。没有计费/令牌监测能力时不承诺金额封顶；用户给出金额预算而无法测量时说明局限，提出并发与尝试次数等可执行边界。时限只能在工具可控制范围内执行，不能假称可强制打断不可中断操作。

每个根任务默认最多两次失败后的自动重试（首次尝试不算重试），每次要有新证据、修正或可判断的暂时性故障原因，禁止原样无限重跑。在无新增证据的相同错误重复出现、超过重试次数、预算/环境边界或缺少必要输入时停止受影响任务，保存成果并报告阻碍。只读诊断和不依赖该任务的工作可以继续。不要为此自动升级或换模，升级仍遵循独立规则。

主 Agent 可以在相同目标、范围、资源边界内接管剩余工作并记录原因，但不能以接管逃避重试限制或继续相同失败操作。外部操作结果不明时先检查状态，避免重试造成重复发送或发布。

## 交接、版本与验收

给下游交接：根任务和修订号、输入版本、接口约定、实际产物位置、已完成事项、验证结果、剩余问题及依赖。不仅交一段总结；下游必须可以访问证据。前置条件未满足时标记阻塞，不让成员假设完成。

将审查绑定具体提交或文件快照/内容哈希，包含工作区未提交改动和相关输入。若不能建立不可变版本，明确记录审查时的内容并标注验证局限，不能把可变路径本身当版本。最终差异发生变化时，根据依赖重新打开受影响验收项，只补查相关风险，不机械全量重测。

任务状态采用：待分配、待开始、运行中、阻塞、待验收、完成、暂停、取消。成员报告完成时只进入“待验收”。主 Agent 核对实际产物、修改范围、接口和相关验证证据后才标记完成；发现问题回到运行中或阻塞，保留历史。旧状态不得覆盖新修订结果。

每项验收记录条件、审查对象版本、证据、检查人和时间、状态（通过/未通过/未验证/不适用），不适用须给理由。必要条件未验证时不能称验收通过。不能用多数意见或模型大小裁决；冲突回到代码、数据、实验及用户需求。主 Agent 保留需求判断、公共接口、冲突裁决和最终验收职责。

## 需求变化与效果评估

新增信息不必重新批准原计划；目标、接口或写入范围实质变化时提高任务修订号，识别受影响成员，停止冲突旧工作，更新输入与依赖，通知并确认交接。保留未受影响工作，展示变更后的分工，按用户启动偏好等待。旧修订的迟到结果只能作为参考，不能覆盖新产物。

每个阶段结束汇总可观测的耗时、实际尝试/重试/升级数、已核实发现、返工和未验收项；实际费用或令牌不可得则标注未知。比较混合团队收益时考虑任务难度和证据，不因一次成功宣称更优，也不为测量自动重复昂贵任务。仅当已观察到重复工作、无效审查或交接过重时建议减少成员、缩小范围或换预设，由用户决定模型/团队变更。
