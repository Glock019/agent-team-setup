# 团队预设

这些是按常见协作模式设计的推荐组合，不是经过基准测试的官方最优配方。主 Agent 保持当前模型，负责需求、公共文件和最终集成；下表全部指子 Agent。A 为同模型双岗位，B–F 至少包含两种不同模型。主 Agent 的模型不计入子团队模型数量。

## 能力分配依据

- `gpt-6-astra`：当前工具声明定位为复杂、高要求任务的高能力模型，安排疑难根因、架构权衡、科学推理及关键审查，不用于简单摘录。
- `gpt-6.1-sol`：当前工具声明及官方子 Agent 文档支持用于多步骤、需要规划和验证的工作，安排实现、修复和交付闭环。
- `gpt-6-luna`：当前工具声明及官方文档定位为快速、范围明确的执行模型，安排字段核对、重复转换、明确测试用例和局部修复。`max` 增加推理投入，不意味着它变成更大模型，不保证能替代复杂架构判断。

更新模型版本时保留职责、强度、人数和依赖；跨型号替换遵循用户明确指定的覆盖。更新预设目录不自动改写已保存的项目团队或命名自定义方案；用户明确指定旧版本时仍保留该请求。每次使用优先检查当前工具声明；不根据版本号拼造不存在的 ID，不把不同型号当作别名。不要宣称模型在特定学科、视觉或安全上的未经验证优势，不给出未经核实的价格和速度比例。

参考：[OpenAI 模型目录](https://learn.chatgpt.com/docs/models)、[OpenAI 子 Agent 文档](https://learn.chatgpt.com/docs/agent-configuration/subagents)及当前会话工具声明，核对日期 2026-10-13。精确价格、可用性或新模型比较需要重新查官方说明。

## 快速选择

| 编号与模式 | 子 Agent 配置（模型 / 强度 / 职责） | 优点 | 适用范围与代价 |
|---|---|---|---|
| A 轻量双人协作 | Luna / medium / 结构与依赖扫描；Luna / high / 逐项核对、明确用例或局部实现 | 同模型按职责和强度分工；协调开销较小 | 日常小改、代码初审、批量核对；复杂根因由主 Agent 处理，不承诺实际费用最低 |
| B 实现与独立审查 | Sol / high / 功能实现；Luna / high / 接口与回归风险审查 | 实现与审查职责分离，用不同模型视角补充检查 | 常规功能和缺陷修复；审查最终代码需要等待实现完成 |
| C 架构与模块开发 | Astra / high / 架构及接口契约；Sol / high / 核心模块；Luna / high / 独立配套模块 | 将复杂决策与具体实现分开，契约稳定后并行开发两个模块 | 跨模块功能、重构；架构阶段先行，存在集成成本 |
| D 故障定位与修复 | Astra / xhigh / 因果分析与根因假设；Luna / high / 日志、调用链和复现证据；Sol / high / 实现修复并验证 | 将假设、证据和修复连接起来，避免只处理报错表象 | 训练异常、并发或跨模块故障；前两者可并行，修复依赖诊断结果 |
| E 科研代码与稿件核对 | Astra / high / 方法与实验逻辑审查；Luna / high / 代码流程和实现证据；Luna / max / 公式符号、数值、表格及引用位置逐项核对 | 复杂方法判断、实现追踪、细项核对各有负责人，便于建立可追溯的问题清单 | 论文与代码一致性、实验审核；默认全只读，不能以模型意见替代实验和原始数据 |
| F 对抗式方案审查 | Sol / high / 独立提出可实施方案；Astra / xhigh / 独立找反例和关键约束；Luna / high / 把验收标准转成明确测试案例 | 同时考虑可行路径与失效条件，并用测试约束主 Agent 的选择 | 重要设计、算法改动；增加模型开销，不按投票决定对错 |

## 每种模式的执行边界

A：扫描和独立核对可并行；若局部实现依赖扫描结论，先扫描。没有修改授权时两个角色均只读。

B：审查者可先依据需求设计检查项；实现完成后必须检查实际最终差异，不能把对旧代码的审查作为新代码通过验收的依据。

C：先确定接口契约，再启动两个互不重叠的模块写入。架构 Agent 提交建议，公共定义由主 Agent 修改。契约发生变化时通知受影响的开发者并重验接口。

D：给根因分析者和证据收集者同一份原始输入，持续交换新证据。确认足以支持修复的原因后再让修复者改代码，不能为了并行让其猜测并改写同一模块。

E：三个角色独立读取相关原始材料；主 Agent 对齐“稿件位置—代码位置—证据—问题”。缺少代码、数据或全文时标注无法核实，不补造结果。

F：先给方案者和质疑者相同原始需求，不预先泄露另一方结论。测试者从用户验收条件提出用例，之后再合并讨论与验证。只有具体证据支持时才否定或采纳方案。

## 选择与调整规则

用户选择编号或名称即选择完整组合，不再重复问同一套模型和规模。展示所选组合的一个主要优点和一个适用边界。可接受“B，但审核改为 Astra high”“E，Luna 改为 medium”等覆盖。

对未定方案按实际任务推荐：小范围核对 A，常规实现 B，跨模块设计 C，疑难故障 D，科研一致性 E，重要方案论证 F。不因看到论文或报错关键词就自动启动最高强度方案。

执行前核对每个 ID、强度和并发上限。若选定组合不可用，列出哪些角色受影响和建议替代，等待用户选择；不要静默换模。用户事先授权自动适配时，按职责选择支持的替代并展示最终映射，仍应保留至少两种模型；若环境仅有一种模型，说明混合配置不可实现，提供单模型或顺序执行选择。

用户减少规模时合并职责到主 Agent，不强行创建空任务。依赖阶段可以先后启动，并发上限不等于团队累计人数；三角色模式在并发上限为二时可以分阶段完成。混合方案调整后尽量保持至少两种子模型；A 或用户明确要求的同模型组合按同模型团队展示。
